## 三、待办（按建议优先级）

### P0 — 并发闸门（spec 承诺过，代码未落地）

**这是当前唯一一处「设计文档写了、实现没跟上」的地方。**

| 项 | 证据 |
|---|---|
| 规范要求 | `docs/specs/2026-08-21-starwhisper-design.md:96`「全局信号量 ≤3；超额 HTTP 429」，:188 列出 `429 BUSY` |
| 已有设计 | `docs/plans/2026-08-24-starwhisper-m2-impl.md:175` 已定 `SolveSlot(max_active=3, max_queue=5)` |
| 实际状态 | `server/routers/identify.py` 全文无 `Semaphore` / `SolveSlot` / `429` / `BUSY`；`server/services/` 无对应模块；`test_concurrency.py` 不存在 |
| 商业影响 | `docs/business/2026-09-11-monetization-feasibility.md:109` 已列为头号容量风险 |

**为什么值得做**：解算是 CPU 密集 + 同步阻塞，单次 5–22s（与文件大小无关，由视场和星点密度决定）。
演示时连续点击或自己开多标签页会直接打挂上游——这是主卖点最容易翻车的地方，
且答辩文档已主动把它列为已知短板，评委很可能当场追问。

**实现要点**（plan 已有完整设计，照做即可）：
- `SolveSlot`：`@asynccontextmanager async def acquire()`，先占 active/queue 再解Semaphore
- 队列满时抛 `BusyError` → HTTP 429 `BUSY`，**不要用嵌套 `async with`**（会卡死 Semaphore）
- 测试需 `@pytest.mark.asyncio`，并发 waiter 测 Busy 走不同任务
